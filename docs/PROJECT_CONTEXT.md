## 3. Уже согласованные требования к модели

### 3.1 Три независимых виртуальных потока

- `Compute`: одна вычислительная задача за раз, в выбранном допустимом порядке.
- `Load`: CPU→GPU, один transfer за раз.
- `Unload`: GPU→CPU, один transfer за раз.
- Потоки независимы и могут перекрываться; скорости H2D и D2H **задаются пользователем отдельно**. В базовой модели `transfer_time = bytes / bandwidth`.
- **Стратегия выбирает как загрузки, так и выгрузки**, в том числе их порядок и предзагрузку на далёкое будущее. Весь граф доступен стратегии (offline planning). Начатые передачи в первой версии не отменяются.
- Compute-задача может начаться только при полной готовности всех требуемых хэндлов/чанков; на время вычисления они pinned и не вытесняются.

### 3.2 Compute ordering — важная поправка пользователя

Поддержать три режима:
1. `trace` — наблюдаемый порядок старта задач в `.rec`;
2. `topological` — топологическая сортировка графа зависимостей, **режим по умолчанию**;
3. `custom` — пользовательский порядок, который должен удовлетворять зависимостям.

**Не заменять topological на trace по умолчанию!** Пользователь уже наблюдала в предыдущих экспериментах, что топологическая сортировка давала меньший makespan. Для честного сравнения memory policies порядок Compute должен быть одинаковым. В перспективе — совместная оптимизация Compute и transfers.

### 3.3 GPU memory

- `gpu_memory_bytes` — **пользовательский параметр**, не зашивать прежний лимит 1349 МиБ.
- Размеры хэндлов различны.
- Два настраиваемых режима физической передачи и вытеснения: `handle` (целый хэндл) и `chunk` (независимые фиксированные чанки, последний может быть меньше). Это нужно для честного сравнения традиционных LRU/Belady с новым chunk-based алгоритмом.
- Для вычисления нужны **все чанки** требуемого хэндла.
- По умолчанию неполный чанк занимает фактический размер; возможно добавить опцию фиксированного слота.
- GPU-память резервируется **перед** началом Load или Compute, включая место под создаваемые выходы; никогда не превышает лимит.
- Dirty/clean: актуальная копия на CPU или GPU, версии данных. CPU-копия не исчезает при загрузке.
- `DROP`: мгновенно освобождает GPU-память, если CPU-копия актуальна или данные больше никогда не нужны (даже если dirty).
- `UNLOAD`: физическая GPU→CPU передача для сохранения новой версии; GPU-память освобождается **только после завершения передачи**, если планируется вытеснение. Возможен `evict_after=false` (сохранить CPU-копию, но оставить данные на GPU).
- `LOAD`: резервирует GPU-память и загружает актуальную CPU-версию; готовность — после завершения.
- `WRITE`: по завершении Compute обновляет GPU-версию и делает CPU-копию устаревшей.
- Состояния: `UNINITIALIZED`, `CPU_ONLY`, `BOTH_CLEAN`, `GPU_DIRTY`, плюс активные операции loading/unloading, pinned.
- Некорректные планы стратегии должны выявляться движком, а не молча исправляться.

### 3.4 Cold start, warm start, повторы

- В самом начале исходные **значения входных данных** доступны на CPU, GPU пуста.
- Стратегия может предзагрузить данные **до первой Compute-задачи**; время этого прогрева учитывается в makespan холодного старта.
- Выходные данные, впервые полностью создаваемые задачей, не требуют фиктивного CPU→GPU переноса, но требуют GPU-память до старта Compute.
- Между микробатчами и полными training steps GPU **не очищается автоматически**; persistent-данные могут оставаться на GPU.
- Цель исследований — установившееся размещение памяти (`start ≈ end` по резидентности), но значения весов/версии меняются; steady state измеряется, не навязывается.
- Полный `training step` (включая микробатчи и optimizer step) — естественная единица повторения. В перспективе повторять граф несколько раз с сопоставлением логических хэндлов, разными входами и сохранением параметров/состояний Adam.
- Начать с границ, когда все три потока завершили действия шага, затем допустить предзагрузку следующего шага до завершения текущего.

### 3.5 Доступы и семантика StarPU

- В трассах встречаются `R`, `W`, `RW`, `RWC`; **не сводить всё к трём режимам без проверки**.
- Обсуждалось: `R` требует актуальное содержимое; `RW` требует старое и записывает новое; `RWC` (commutative read-write) для единственного последовательного Compute-потока предположительно моделируется как `RW` при сохранении исходного режима.
- `W` обычно write-only по объявлению доступа StarPU, но конкретные операции NNTile (особенно Adam states) требуют проверки реализации: нельзя уверенно утверждать, что прежние значения не нужны, только по имени или `W`.
- Сохранять оригинальный режим из `.rec`, вводить явно проверенную таблицу семантики. До проверки использовать консервативные допущения и маркировать их.

- В `mbs1` есть 17 завершённых задач без `Iteration`: 15 `nntile_copy`, 1 `nntile_clear`, 1 `nntile_fill_fp32_fast_tf32`; **не отбрасывать их при построении полного графа**.
- В `mbs1` каждый микробатч использует ~956 уникальных хэндлов, ~954 повторяются во всех четырёх; одинаковые handle IDs не гарантируют одинаковую семантическую роль (буферы могут переиспользоваться).
- Каждая задача Adam имеет 4 аргумента с режимами `R W W RW`. Предположительно: градиент, состояния `m` и `v`, параметр модели. Роль по позиции аргумента **требует проверки исходников NNTile**.
- По ранее проведённому анализу каждая из четырёх групп 197 хэндлов имеет суммарный размер около 621.9 МиБ, вместе ~2.43 ГиБ, что превышает старый лимит GPU 1349 МиБ. Это не значит, что всё должно быть одновременно резидентно.
- Классы жизненного цикла: persistent (веса, Adam states), reusable (градиентные буферы), temporary (промежуточные результаты), external_input, unknown. **Не считать все объекты после последнего наблюдаемого использования безопасно удаляемыми**, если граф будет повторяться.

## 10. Критически важные договорённости (коротко)

- `topological` — default Compute order; `trace` и `custom` тоже поддержать.
- Пользователь задаёт GPU limit, H2D/D2H bandwidth, chunk size, granularity.
- `DROP` — мгновенно; `UNLOAD` — память освобождается после завершения передачи.
- CPU/GPU versions и dirty-state обязательны.
- Load/Unload независимы, стратегия управляет обоими потоками и видит будущее.
- Время cold-start prefetch включается в makespan.
- GPU state сохраняется между повторениями; важен steady state.
- Полный training step включает `clear`, все микробатчи, Adam и задачи без Iteration.
- Визуализация Gantt + GPU memory обязательна.
- Milestone 1 протестирован, Milestone 2 пока только планируется.

## D. Последняя беседа: нужен настоящий CLI для запуска симулятора

Пользователь хочет **видеть, что делает программа**, и запускать реальные трассы, а не только pytest. Она попробовала:

```bash

```

**Следующий приоритет пользователя:** реализовать реальный CLI `nntile-sim` поверх парсера и `Simulator`, который запускает реальную `.rec`-трассу и выводит makespan, peak GPU bytes, H2D/D2H bytes, completed jobs, при необходимости CSV событий и затем интерактивную Plotly Gantt + memory occupancy. Требуемые флаги: `--gpu-memory-mib`, `--h2d-gbps`, `--d2h-gbps`, `--compute-order` (`topological` default; `trace`, `custom`), выходной CSV/HTML. Проверить API парсера в текущих файлах, **не угадывать имена функций**. CLI надо добавить в `pyproject.toml` `[project.scripts]` и переустановить editable пакет `python -m pip install -e .`. Конверсия GB/s в bytes/us при десятичных GB/s: `GB/s * 1000`. Внимательно проверить единицы времени из `.rec` и `duration_us`.

Внимание: нет доказательства, что существующая модель корректно проходит реальные трассы и даёт достоверный makespan; следует сначала запустить и диагностировать, не заявлять неподтверждённых результатов.
