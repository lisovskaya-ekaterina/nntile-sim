# Offline GPU Memory Scheduling for NNTile

## 1. Цель

Построить корректное глобальное расписание операций:

- Compute — вычисление на GPU;
- H2D — передача данных CPU → GPU;
- D2H — передача данных GPU → CPU;
- DROP — освобождение GPU-памяти.

Основная цель — минимизация makespan, то есть общего времени
выполнения всех задач.

## 2. Входные данные

Используем полную трассу вычислений NNTile.

Для каждой задачи известны:
- длительность Compute;
- используемые хэндлы данных;
- тип доступа (чтение/запись);
- размер данных;
- зависимости задач.

Хэндлы разбиваются на чанки.

В текущих экспериментах:
- GPU memory: 768 MiB;
- chunk allocation: fixed-slot;
- chunk size: 768 KiB;
- H2D bandwidth: 12000 bytes/us;
- D2H bandwidth: 12000 bytes/us.

## 3. Ограничения

1. Общий объём зарезервированной GPU-памяти не превышает capacity.
2. Все чанки задачи находятся в GPU на протяжении Compute.
3. Compute использует актуальные версии данных.
4. Новая версия записываемого чанка появляется в конце Compute.
5. Грязный чанк нельзя удалить, если его актуальная версия
   потребуется в будущем и не сохранена на CPU.
6. Чистый чанк с актуальной копией на CPU можно удалить без D2H.
7. D2H должна завершиться до соответствующего DROP.
8. H2D и D2H имеют отдельные последовательные каналы.
9. Передачи могут перекрываться с Compute при соблюдении
   ограничений памяти, версий и доступа к чанкам.

## 4. Выбор вытесняемых чанков

Базовый алгоритм — Belady.

При нехватке GPU-памяти предпочитаем вытеснять чанк,
следующее использование которого находится дальше всего
в будущем.

При планировании учитываем:
- следующее использование;
- размер чанка;
- размер резервируемого GPU-слота;
- актуальность CPU-копии;
- необходимость и длительность D2H.

Belady — базовая политика выбора жертв.
Глобальная оптимизация makespan может потребовать исследования
альтернативных решений.

## 5. Планирование операций

### 5.1. Прогноз потребности в памяти

Анализируем будущие Compute и определяем моменты,
когда для загрузки новых чанков понадобится память.

### 5.2. Выбор кандидатов на вытеснение

Используем Belady для выбора кандидатов.

Определяем необходимый объём освобождаемой памяти.

### 5.3. Планирование D2H

Для каждого грязного кандидата определяем:

- размер данных S;
- объём освобождаемой памяти M;
- длительность передачи T = S / bandwidth;
- момент готовности актуальной версии;
- допустимые интервалы передачи;
- дедлайн освобождения памяти.

Планируем D2H заранее, чтобы по возможности
перекрыть передачу с Compute.

Выбор порядка передач должен учитывать размеры чанков,
дедлайны и будущую потребность в GPU-памяти.

EDF не является обязательной политикой.

### 5.4. DROP

DROP выполняется после завершения необходимой D2H,
когда требуется освободить GPU-память.

Для чистого чанка D2H не нужна.

### 5.5. H2D и Compute

Планируем H2D с учётом:
- доступной GPU-памяти;
- готовности актуальной CPU-версии;
- занятости H2D-канала;
- будущих Compute.

Compute начинается только после готовности всех
необходимых чанков.

## 6. Метрики качества

### Метрика 1. Полная загрузка одного канала

Требуется, чтобы хотя бы один из трёх каналов:

- Compute;
- H2D;
- D2H;

был занят на протяжении всего makespan.

Обозначим загрузку канала k:

U_k = busy_time_k / makespan

Критерий:

max(U_Compute, U_H2D, U_D2H) = 1

Важно: речь идёт о полной загрузке одного фиксированного
канала, а не о том, чтобы в каждый момент был занят
любой из трёх каналов.

Это целевой критерий первого уровня, а не уже
доказанное свойство текущего планировщика.

### Метрика 2. Минимизация makespan

После достижения первой метрики стремимся минимизировать
общее время выполнения расписания.

Для поиска и оценки оптимума рассматриваем:
- полный перебор на маленьких примерах;
- MIP/ILP;
- сравнение оптимальных решений с эвристическим алгоритмом.

При этом корректность расписания обязательна всегда.

## 7. Экспериментальные результаты

Трасса: examples/tasks_mbs1.rec
Количество задач: 5484

| Алгоритм | Makespan, s | D2H, MiB |
|---|---:|---:|
| Belady-demand | 249.441260 | 14045.00 |
| Prefetch | 248.623778 | 14045.00 |
| Early D2H | 248.008811 | 26193.12 |
| Planned D2H | 248.030962 | 14045.00 |

Planned D2H уменьшает makespan относительно Prefetch
без увеличения D2H-трафика.

Для Planned D2H:
- выполнено 5484 задачи;
- peak GPU memory: 768 MiB;
- H2D: 12035.95 MiB;
- D2H: 14045.00 MiB;
- проверки timeline и D2H/Compute/residency пройдены.

Полная независимая проверка версий данных ещё требуется.

## 8. Текущий статус реализации

Реализовано:
- исходный Belady-demand;
- H2D prefetch;
- экспериментальный Early D2H;
- Planned D2H;
- проверка временных ограничений и размещения;
- извлечение окон для будущих D2H.

На трассе tasks_mbs1.rec получены окна для всех
19535 исходных D2H-передач.

Медианный вычисленный slack: 598.197 ms.
Максимальный вычисленный slack: 77786.582 ms.

Эти окна предварительные и не гарантируют
совместимость всех передач между собой.

## 9. Следующие этапы

1. Реализовать независимую проверку версий чанков.
2. Измерять загрузку Compute, H2D и D2H.
3. Построить план будущих вытеснений по Belady.
4. Планировать D2H с учётом размеров и потребности в памяти.
5. Перестраивать DROP, H2D и Compute по глобальному плану.
6. Реализовать точный оптимизатор для небольших задач
   (перебор или MIP/ILP).
7. Сравнивать эвристическое расписание с оптимальным.

## 10. Правило разработки

Каждое существенное изменение алгоритма сопровождается:

- обновлением этого документа;
- тестами корректности;
- измерением makespan;
- измерением загрузки трёх каналов;
- измерением H2D/D2H-трафика и peak GPU memory.

Новые гипотезы не записываем как доказанные результаты.
