# NNTile Simulator — глобальное планирование вычислений и GPU-памяти

> **Статус:** техническое описание исследовательской модели и текущего направления разработки. Документ заменяет историческое описание Prefetch / Early D2H / Planned D2H. Детали конкретных эвристических преобразований следует сверять с кодом при каждом изменении алгоритма.

## 1. Цель

По известной заранее трассе задач NNTile построить **корректное расписание** вычислений и перемещений данных между CPU и GPU с минимальным временем завершения (**makespan**).

Планировщик принимает решения о том, **какие данные и когда загрузить, сохранить, вытеснить или оставить в GPU**, а также когда запустить вычислительные задачи. Корректность — обязательное ограничение; минимизация makespan — цель оптимизации.

## 2. Входные данные и модель

Для вычислительных задач известны длительность, используемые хэндлы, режимы доступа и зависимости. Известны размеры данных, ёмкость GPU-памяти и скорости передач. Хэндлы могут быть представлены чанками; для выделения памяти используется модель размещения, в частности `fixed-slot`.

Моделируются три отдельных последовательных ресурса:

| Ресурс | Операция | Длительность |
|---|---|---|
| Compute | Вычисление на GPU | Задана трассой |
| H2D | Копирование CPU → GPU | Размер передаваемых данных / скорость H2D |
| D2H | Копирование GPU → CPU | Размер передаваемых данных / скорость D2H |

Операция **DROP** освобождает GPU-память. Она не является четвёртым каналом передачи. Операции на разных ресурсах могут перекрываться, если это допускают зависимости, версии данных и ограничения памяти.

## 3. Инварианты корректного расписания

1. В любой момент занятая или зарезервированная GPU-память не превышает заданную ёмкость.
2. Все чанки, необходимые Compute, присутствуют в GPU на протяжении **всего** выполнения этой задачи.
3. Compute запускается только после завершения необходимых зависимостей и подготовки актуальных данных.
4. Новая версия записываемого чанка возникает **по завершении Compute**.
5. Чистые данные с актуальной CPU-копией можно вытеснить без D2H.
6. Грязные данные, актуальная версия которых ещё потребуется, нельзя потерять: перед освобождением должна быть обеспечена возможность получить эту версию в будущем, в том числе посредством D2H.
7. Если для освобождения чанка нужна D2H, она должна завершиться **до** соответствующего DROP.
8. Каждый из каналов H2D и D2H выполняет не более одной передачи одновременно; Compute — не более одной вычислительной задачи одновременно в принятой модели.
9. Перекрытие D2H и Compute допустимо лишь при отсутствии конфликтов доступа к данным и нарушений версионности.

## 4. Что оптимизируем

Основная метрика:

**Makespan = время завершения последней обязательной операции расписания.**

Дополнительно измеряются:

- время занятости и простоя Compute, H2D и D2H;
- объём H2D/D2H-трафика и число передач;
- пиковая занятость GPU-памяти;
- число и длительность задержек запуска Compute;
- разрыв между эвристическим решением и доступной нижней оценкой либо точным оптимумом.

Загрузка ресурса: `utilization = busy_time / makespan`.

**100% загрузка хотя бы одного канала не является необходимым условием оптимальности.** Даже оптимальное расписание может иметь неизбежные простои из-за зависимостей, памяти и невозможности раньше подготовить данные. Поэтому загрузка каналов — диагностический показатель, а не отдельное жёсткое требование.

## 5. Подход к глобальному планированию

В отличие от локальной политики вытеснения, глобальный планировщик использует сведения о будущих задачах. Он рассматривает взаимосвязанные решения:

1. **Compute:** порядок и возможное время запуска задач с учётом зависимостей.
2. **Резидентность:** какие чанки оставить в GPU для повторного использования.
3. **H2D:** какие данные подготовить заранее и не создать при этом конфликт по памяти.
4. **D2H:** какие грязные версии сохранить и в какие интервалы возможно выполнить передачу.
5. **DROP:** когда освобождение памяти действительно необходимо и безопасно.
6. **Оптимизация:** какие изменения расписания сокращают ожидание Compute или общий makespan.

Belady (вытеснение данных с наиболее далёким следующим использованием) служит **базовой эвристической идеей**, но не гарантирует оптимальный makespan. На результат влияют размер данных, стоимость передачи, занятость каналов, возможность перекрытия и будущая потребность в памяти.

Важное различие: чанк может **стать кандидатом на вытеснение** после использования, но это не означает, что его следует немедленно выгружать или удалять. Момент операции выбирается исходя из общего расписания.

## 6. Текущая структура реализации

Основной интерфейс глобального планировщика:

`src/nntile_sim/core/global_planner.py`

Компоненты планирования:

| Файл в `src/nntile_sim/core/scheduling/` | Область ответственности |
|---|---|
| `planner.py` | Построение глобального расписания |
| `baseline.py` | Базовые стратегии и исходные варианты |
| `bounds.py` | Нижние оценки времени выполнения |
| `optimization.py` | Преобразования для улучшения расписания |
| `packing.py` | Размещение данных при ограниченной памяти |
| `residency.py` | Учёт присутствия данных в GPU |
| `residency_search.py` | Поиск альтернатив размещения и вытеснения |
| `prefetch_cleanup.py` | Обработка предварительных загрузок |
| `writeback.py` | Сохранение изменённых данных |

Связанные модули:

- `src/nntile_sim/core/engine.py` — движок симуляции и базовые политики;
- `src/nntile_sim/core/exact_small.py` — точный решатель для небольших постановок;
- `scripts/validate_global_planner.py` — проверка сформированного расписания;
- `scripts/benchmark_nntile_graph.py` — сравнение LRU-demand, Belady-demand и Global Planner.

Названия и назначение компонентов описывают архитектуру; точный порядок вызовов и условия применения каждой эвристики определяются кодом.

## 7. Проверка оптимальности на малых задачах

Для небольших примеров используется `exact_small.py`: поиск минимального времени по пространству допустимых состояний и событий. Он позволяет сравнить эвристику с **точным оптимумом в рамках той же модели и допущений**.

При сравнении должны совпадать: задачи, порядок Compute (если зафиксирован), размеры чанков, вместимость GPU, скорости H2D/D2H, модель слотов, правила версионности и допустимые операции.

Если `heuristic_makespan > exact_makespan`, это контрпример оптимальности текущей эвристики. Его нужно сохранить как регрессионный тест и исследовать, **какое решение планировщика вызвало задержку**: выбор жертвы, момент DROP, порядок D2H, время H2D, удержание данных или иное ограничение.

Равенство точному решению на конечном наборе примеров **не доказывает глобальную оптимальность** алгоритма.

## 8. Проверка корректности

Используются два взаимодополняющих подхода:

- **Автоматические тесты** (`tests/`), включая сравнение Global Planner с точным решателем на небольших сценариях.
- **Проверка событийного расписания** (`scripts/validate_global_planner.py`): временные интервалы, каналы, вместимость GPU, доступность данных, некоторые условия версий и безопасного вытеснения.

Наличие валидатора не означает, что все возможные ошибки версионности и конкурирующего доступа формально исключены. Расширение независимых проверок — отдельная задача разработки.

Запуск тестов из корня проекта:

```bash
python -m pytest -q
```

Запуск дополнительной проверки:

```bash
python scripts/validate_global_planner.py
```

## 9. Экспериментальная методика

Для каждого изменения эвристики:

1. Проверить корректность на малых сценариях и регрессионных примерах.
2. Сравнить makespan с точным оптимумом там, где это вычислительно возможно.
3. Запустить репрезентативные трассы NNTile и сравнить с базовыми политиками.
4. Зафиксировать makespan, нижнюю оценку, простой каналов, H2D/D2H-трафик и пиковую память.
5. Сохранить контрпримеры и не допускать регрессий на ранее исправленных случаях.

Пример сравнения на реальной трассе:

```bash
python scripts/benchmark_nntile_graph.py examples/tasks_mbs1.rec \
  --capacities-mib 768 1024 1536 \
  --h2d-gbps 12 --d2h-gbps 12 \
  --chunk-mib 1 \
  --output results/global_comparison/benchmark.csv
```

Параметры конкретного эксперимента не следует считать универсальными параметрами алгоритма.

## 10. Известные ограничения и дальнейшая работа

- Global Planner — **эвристический планировщик**; для произвольных трасс оптимальность не гарантирована.
- Набор регрессионных сценариев не исчерпывает всех возможных сочетаний размеров, зависимостей, версий и конкуренции ресурсов.
- Точный решатель применим только к ограниченным по размеру задачам и к поддерживаемым им допущениям.
- Требуется продолжать поиск контрпримеров, анализ причин неоптимальности и развитие независимой проверки корректности.
- На реальных трассах нижние оценки помогают измерять качество, но не обязательно равны достижимому оптимуму.
