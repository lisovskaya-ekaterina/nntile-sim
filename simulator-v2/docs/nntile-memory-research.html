Как управлять GPU-памятью, когда данных больше, чем места?

Исследуем, какие данные оставлять на GPU, какие вытеснять и как на объём передач влияют алгоритм, размер чанка и способ выделения памяти.

Проблема

Вычислительная задача требует несколько объектов данных. Если все они не помещаются в GPU-память, часть уже загруженных данных нужно удалить. Неудачное решение приводит к повторным H2D-передачам и, для изменённых данных, D2H-передачам.

Наш подход

Берём реальную трассу задач NNTile и воспроизводим её в контролируемой модели. Меняем только исследуемые параметры и сравниваем трафик, время исполнения и состав GPU-кэша.

Это исследовательский симулятор, а не точная модель производительности StarPU или конкретного GPU. Он помогает изолировать механизмы управления памятью.

Код и методика: nntile-sim / simulator-v2. Результаты зафиксированы до коммита eca0254.

01 / Что именно моделируем

Есть последовательность Compute-задач, каждая читает или записывает набор объектов (хэндлов). GPU имеет ограниченную ёмкость M. Перед выполнением задачи все необходимые ей данные должны находиться в GPU; эти данные защищены от вытеснения.

CPU-память
исходные и сохранённые данные
⇄
GPU-кэш
ограниченная ёмкость M
→
Compute
очередная задача

Передачи

H2D — загрузка данных из CPU в GPU. D2H — сохранение изменённых (dirty) данных обратно в CPU, если они ещё нужны.

Ttransfer = B / vB — передаваемые байты, v — пропускная способность

Что упрощено

Для сравнения алгоритмов используем последовательный demand-only режим: загружаем данные только перед требующей их задачей, без prefetch и перекрытия Compute с передачами.

Время Compute берётся из трассы.

Зачем нужны чанки

Большой объект можно разбить на чанки размера C, чтобы вытеснять часть объекта, а не весь объект сразу.

N = ⌈S / C⌉S — размер объекта; последний чанк может быть короче C

В нашей модели задача, обращающаяся к объекту, требует все его чанки. Однако между задачами чанки могут вытесняться по отдельности.

Для всех сравниваемых запусков используется один детерминированный топологический порядок задач. Симулятор ведёт учёт резидентных и dirty-данных, ограничивает объём GPU и записывает события ALLOC, LOAD, UNLOAD, DROP и Compute.

Независимые проверки журналов подтверждают согласованность событий, ёмкости GPU и числа выполненных задач. Исходники: core/engine.py, chunks.py, sim_cli.py; инструменты проверки находятся в scripts/.

03 / Две политики вытеснения

LRU — Least Recently Used

Удаляем чанк, к которому дольше всего не обращались. Используется информация только о прошлом.

victim = arg minc last_use(c)

Практичный базовый алгоритм, не требующий знания будущей трассы.

Belady — farthest next use

Удаляем чанк, следующее использование которого находится дальше всего в будущем (или отсутствует).

victim = arg maxc next_use(c)

В симуляторе будущие обращения известны из трассы.

При равенстве приоритетов выбирается чанк с меньшим фактическим payload; затем применяется детерминированное разрешение равенства. Чанки текущей задачи не вытесняются.

Для объектов разных размеров и чанковых моделей правило «дальше всего в будущем» не является доказанно оптимальным по общему объёму переданных байтов. Это важное ограничение и мотивация для size-aware алгоритмов.

04 / Посмотрим, как работает вытеснение

Небольшой учебный сценарий, основанный на тестах симулятора. Размеры здесь указаны в байтах, а не MiB, чтобы было удобно проследить каждое действие.test_partial_chunk_eviction и test_partial_dirty_chunk_writeback. Размеры здесь указаны в байтах, а не MiB: это намеренно маленький пример для проверки семантики.

Без чанков

GPU = 12 байт. Хэндл A = 10 байт хранится целиком. Чтобы загрузить B = 4 байта, A приходится вытеснить полностью.

10 + 4 > 12

С чанками по 4 байта

Хэндл A = A:0 (4) + A:1 (4) + A:2 (2). Каждый чанк занимает 4 байта GPU. Для B достаточно вытеснить только A:2.

3 · 4 = 12;   W = 12 − 10 = 2
СЦЕНАРИЙ

Загрузка A

Начальное состояние

GPU: 0 / 12 байтH2D: 0 байтD2H: 0 байт

Шаг 1

Важная оговорка: в нечанковой модели GPU учитывает фактический размер хэндла (10 байт), а в чанковой — полные слоты (12 байт). В сценарии с записью D2H выполняется только для грязного чанка, если его значение потребуется позже. Иллюстрации отражают выбранную последовательность из тестов, а не общий результат всех трасс.

Что показывает этот пример

Обратите внимание на три правила: (1) Compute требует резидентности всех нужных чанков; (2) GPU резервирует полный слот, но передаёт только payload; (3) при равном LRU/Belady-приоритете вытесняется чанк с меньшим payload. В тестовом примере это A:2, а не A:0.

05 / Почему способ выделения памяти важен

Чанк содержит фактические данные (payload), но GPU-аллокатор может резервировать под него больше места. Мы сравнили две модели.

fixed-slot

Каждый резидентный чанк занимает полный слот C, даже если последний чанк объекта меньше.

Mreserved = N · C
W = N · C − SДля полностью резидентного объекта; W — внутренняя фрагментация

exact-size

Каждый чанк занимает ровно столько GPU-памяти, сколько содержит данных. Внутренняя фрагментация слотов отсутствует, но вытеснение по-прежнему происходит целыми чанками.

Mreserved = S
W = 0Для полностью резидентного объекта в принятой модели

Пример: объект 10 MiB, чанк 8 MiB

МодельЧанкиЗанято GPUПотери
fixed-slot8 + 2 MiB16 MiB6 MiB
exact-size8 + 2 MiB10 MiB0 MiB

Объём H2D/D2H в обеих моделях определяется фактическим payload, а не размером зарезервированного слота.

Что видно на графике

На этой трассе Belady даёт меньший H2D-трафик, чем LRU, при всех проверенных размерах чанка. Для fixed-slot рост чанка сопровождается ростом трафика у обеих политик. Но эти данные сами по себе не разделяют эффект фрагментации и гранулярности вытеснения.

Корреляция размера чанка и трафика не доказывает, что рост вызван исключительно округлением слотов. Вытеснение на уровне чанков также меняет последовательность решений.

Результат 3. Почему Belady всё ещё зависит от размера чанка?

Даже при exact-size удаляется целый чанк. В журнале перед Compute-задачей 1758 при 4 MiB освободилось 4 MiB, а при 8 MiB — 8 MiB. В результате для одного хэндла в GPU осталось соответственно 140 и 136 MiB.

Belady 4 MiB

140 MiB резидентно, диапазон [0, 140) MiB.

Belady 8 MiB

136 MiB резидентно, диапазон [0, 136) MiB.

Анализатор резидентных диапазонов обнаружил различия после 4441 из 5484 Compute-задач; первое — после позиции 403 (job_id=1758). Перед задачей 13771 в конфигурации 4 MiB потребовалась дополнительная H2D-загрузка 3 MiB, которой не было при 8 MiB. Прямая причинная цепочка между этими двумя эпизодами отдельно не устанавливалась.

Итог: размер чанка влияет на память двумя разными способами. Фрагментация зависит от модели аллокации; гранулярность вытеснения сохраняется даже в exact-size. Оба механизма важны для оценки алгоритмов.

08 / Как воспроизвести

Пример запуска Belady с чанками 4 MiB в режиме exact-size из каталога simulator-v2:

python -m nntile_sim.sim_cli \
  ../examples/tasks_mbs1.rec \
  --gpu-memory-mib 2048 \
  --chunk-size-mib 4 \
  --chunk-allocation exact-size \
  --h2d-gbps 12 --d2h-gbps 12 \
  --memory-policy belady-demand \
  --compute-order topological \
  --events-csv results/milestone5_3/belady_4mib_exact_events.csv

Проверка и сравнение:

python scripts/validate_chunk_events.py \
  results/milestone5_3/belady_4mib_exact_events.csv \
  --capacity-mib 2048 --chunk-mib 4 --chunk-allocation exact-size
python scripts/compare_chunk_residency.py
python -m pytest -q

CSV экспериментов хранятся локально и исключены из Git. Подробные результаты: docs/milestone5_3-results.md и docs/milestone5_4-results.md. Последний подтверждённый запуск тестов: 52 passed, 2 xfailed (после Milestone 5.3).
