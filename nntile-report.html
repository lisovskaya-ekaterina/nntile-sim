Как планировать память GPU по всему графу

Симулятор заранее строит расписание задач и перемещений данных при фиксированном порядке вычислений. Версия V12 учитывает, сколько времени потребуется, чтобы освободить место, и когда вытесненные данные понадобятся снова.

Что выбирает планировщик

Из трассы известны зависимости, хэндлы, режимы доступа и длительности задач. После выбора допустимого порядка Compute планировщик определяет моменты LOAD (CPU → GPU), UNLOAD (GPU → CPU), ALLOC, DROP и запуска Compute. Цель — минимизировать время конца последней операции, включая пересылки.

Каждый из трёх каналов выполняет одну операцию за раз. Разные каналы могут работать параллельно. Каждый хэндл разбит на чанки. В режиме fixed-slot последний неполный чанк резервирует целый слот, а время его пересылки определяется фактическим объёмом данных и скоростью канала.

Память занята с начала LOAD. Все чанки задачи остаются на GPU до конца Compute. Запись создаёт новую версию в конце вычисления. Чистую копию можно удалить сразу после использования. Если грязная версия ещё понадобится для чтения, её сохраняют до DROP. Полная перезапись W допускает удаление прежнего значения. В этой модели конечные результаты специально на CPU не выгружаются.

Как V12 строит расписание

  1. Индексирует будущие обращения. Для каждого чанка известны задачи, которые будут его читать или записывать. На временной шкале без простоев начало задачи задаёт желаемый срок готовности её входов.
  2. Планирует размещение. Сроки H2D рассчитываются от потребителей назад. Планировщик учитывает очередь загрузок, занятые слоты, следующее использование и актуальность версии. Для выхода с доступом W достаточно зарезервировать место.
  3. Расставляет операции во времени. Для каждого варианта вычисляет ранние допустимые старты по готовности данных, каналов и памяти. UNLOAD и DROP — отдельные события. Между ними чанк можно читать, когда передача уже завершилась.
  4. Пробует альтернативы, пока есть разрыв с нижней границей. Варианты включают раннюю D2H после записи, удержание данных между чтениями, раннее удаление устаревших версий, другой порядок H2D и предзагрузку следующей задачи. Возможно отложить чтение для окончания D2H. Близ крупных пауз V11 проверяет до 24 вариантов вытеснения выбранного хэндла после конкретной задачи.
  5. Сравнивает время освобождения памяти. V12 дополнительно пробует варианты с предзагрузкой и ранним вытеснением. При дефиците предпочтение получает кандидат, освобождающий достаточно байтов. Затем сравниваются оценка момента освобождения и запас времени для возврата к следующему чтению. При ожидаемом дефиците отдельный вариант раньше выгружает чанки, пропускающие следующую задачу, начиная с меньшего объёма данных.
  6. Выбирает по полному makespan. Оценка кандидата служит для построения плана. Выигрыш проверяется на расписании всех операций с реальным лимитом памяти. При достижении нижней границы дальнейший поиск прекращается.
Как проверяем оптимальность. Для каждой задачи i складываем время обязательных начальных H2D к её старту и длительность всех Compute от i до конца. Максимум этих сумм и общего времени Compute — нижняя граница. Совпадение с корректным расписанием доказывает оптимальность в модели. При положительном разрыве граница может быть слабой. Для малых графов отдельный решатель перебирает состояния памяти и каналов. При исчерпании бюджета результат остаётся открытым.

Два одинаковых слота, два времени освобождения

Граф 8049 содержит семь задач. GPU вмещает 8 байт, размер слота — 2 байта. Чанк B содержит 1 байт, D — 2 байта. В 3 мкс заканчивается T1 и требуется место для загрузки A. Скорости H2D и D2H составляют соответственно 1 и 2 байта/мкс.

Ось времени — мкс. V11 сначала сохраняет D. V12 сохраняет B за 0,5 мкс и сразу начинает загрузку A. Параллельно D уходит на CPU. Во время T2 возвращается B, а во время T3 — D. Точный перебор подтвердил 17,5 мкс. В этом случае дополнительный трафик сокращает makespan.

Малые графы. V12 повторила точный минимум на 450 ранее проверенных графах. На 30 дополнительных графах с несколькими чанками на хэндл (seed 8050–8079) валидатор расписания прошёл во всех случаях. В 28 случаях полный перебор подтвердил оптимальность. В двух сработал лимит поиска 30 000 состояний. Универсального доказательства оптимальности эвристики нет.

От V3 до V12

ВерсияЧто изменилось
V3Будущие обращения известны. Вытеснение учитывает дальность следующего использования. Предзагрузка и ранняя выгрузка ориентированы на ближайшую задачу.
V4–V5V4 сдвигает выбранные операции к ранним допустимым стартам. В V5 запас 96 МиБ на этапе выбора вытеснений устранил простой на mbs1 ценой роста трафика.
V6–V7V6 рассчитывает сроки от потребителей с реальным лимитом памяти. V7 переносит выгрузку в свободное окно после последней записи. На mbs4 это устранило оставшиеся 12,665 мс простоя.
V8–V9Появились нижняя граница, диагностика пауз, сравнение политик и независимый точный решатель. V9 отменяет загрузку, если её результат вытеснен до использования.
V10–V11Сравнение удержания с ранним освобождением, в том числе при полной перезаписи. Поиск порядка передач разной длины и вариантов ранней D2H с возможной задержкой чтения.
V12Выбор между вытеснениями с разной длительностью D2H при одинаковом резервировании слота. Учитываются стоимость возврата и перекрытие передач с Compute.

Как воспроизвести

Распакуйте архив V12 в корень проекта nntile-sim. Из корня проекта в активном окружении выполните:

export PYTHONPATH=simulator-v2/src
python -m unittest discover -s simulator-v2/tests -p test_global_v12.py
python simulator-v2/scripts/validate_global_v12.py
python simulator-v2/scripts/validate_global_v12.py examples/tasks_mbs4.rec

Интерактивная среда экспериментов — NNTile Dashboard

Для запуска симуляций и исследования расписаний разработана локальная интерактивная панель NNTile Dashboard. Она использует существующий Python-движок проекта и позволяет запускать алгоритмы на реальных трассах.

Запуск

  1. Откройте терминал в корневом каталоге проекта nntile-sim.
  2. Активируйте виртуальное окружение:
source .venv/bin/activate
  1. Запустите локальный сервер:
python dashboard_server.py
  1. Откройте панель в браузере:
http://127.0.0.1:8765/nntile-dashboard.html

Терминал с работающим сервером необходимо оставить открытым. Для остановки сервера нажмите Ctrl+C.

Настройка эксперимента

  • Выбор входной трассы: tasks_mbs1.rec или tasks_mbs4.rec.
  • Независимый выбор алгоритмов LRU, Belady и Global Planner с помощью отдельных флажков.
  • Настройка объёма GPU-памяти.
  • Настройка пропускной способности H2D и D2H.
  • Настройка размера чанка Global Planner. Значение по умолчанию — 0,75 МиБ.
  • Выбор порядка выполнения Compute.

Результаты и визуализация

  • Сравнение makespan и других показателей симуляции.
  • Временная диаграмма Compute, H2D и D2H.
  • Визуализация использования GPU-памяти.
  • Просмотр отдельных событий расписания.

Все вычисления выполняются локально на Python-движке симулятора. Браузер используется для управления экспериментом и отображения результатов.
