1. Цель проекта

По заранее известной трассе NNTile построить корректное расписание вычислительных задач и перемещений данных между CPU и GPU. Планировщик выбирает, какие данные и когда загрузить, сохранить, оставить в GPU или вытеснить, а также когда запускать Compute.

Главная цель
min makespan
Минимизация времени завершения последней обязательной операции
Жёсткое ограничение
GPU capacity
Занятая и зарезервированная память не превышает заданную ёмкость
Обязательное условие
Correctness
Зависимости, доступность и актуальность версий данных соблюдены

Это исследовательская модель, а не точная копия поведения StarPU или реального GPU. Результаты симуляции характеризуют принятую модель и заданные параметры, а не измеренное время исполнения на физическом устройстве.

2. Модель выполнения

Симулятор моделирует три независимых последовательных ресурса. На каждом ресурсе одновременно выполняется не более одной операции; разные ресурсы могут работать параллельно, если это допускают зависимости, память и правила доступа к данным.

Схема иллюстрирует возможность перекрытия операций, а не конкретное расписание или измеренные длительности.

Ресурс / событиеНазначениеДлительность
ComputeВыполнение вычислительной задачи на GPUЗадана трассой
H2DКопирование данных CPU → GPUРазмер передаваемых данных / скорость H2D
D2HКопирование данных GPU → CPUРазмер передаваемых данных / скорость D2H
DROPОсвобождение GPU-памятиСобытие управления памятью, не отдельный канал

Данные, чанки и версии

  • Хэндлы могут разбиваться на чанки. В модели fixed-slot каждый чанк резервирует слот заданной ширины; последний неполный чанк может занимать полный слот.
  • Время передачи определяется фактическим размером данных, а резервирование GPU-памяти — размером слота.
  • Все чанки, необходимые задаче, должны находиться в GPU на протяжении всего Compute.
  • Новая версия записываемого чанка возникает по завершении Compute.
  • Чистые данные с актуальной копией на CPU можно вытеснить без D2H.
  • Грязные данные, актуальная версия которых понадобится в будущем, нельзя потерять: перед освобождением нужно обеспечить сохранение версии.
  • Если для освобождения необходима D2H, она должна завершиться до DROP. Конечные результаты графа не выгружаются на CPU автоматически, если это не требуется моделью последующего использования.

3. Как работает Global Planner

Global Planner строит расписание не как последовательность «загрузить данные — выполнить задачу — выгрузить данные», а как совместный план трёх ресурсов и GPU-памяти. Решение о вытеснении влияет на будущие передачи; момент передачи влияет на момент освобождения памяти; доступность памяти влияет на запуск Compute. Поэтому локально выгодное действие не обязательно улучшает общее время выполнения.

3.1. Формальная постановка

Пусть трасса содержит множество задач J = {1, …, n}. Для каждой задачи j известны длительность вычисления pj, множество используемых чанков Rj, множество читаемых чанков Readj, множество записываемых чанков Writej и зависимости от предшествующих задач.

План содержит операции трёх типов: Compute, H2D и D2H. У каждой операции есть момент начала s и завершения e. Для операции o длительностью do:

eo = so + do

Целевая функция — минимизировать момент завершения последней операции:

min  Cmax = min  maxo ∈ O eo

Здесь O — все операции, необходимые для выполнения трассы и сохранения тех версий данных, которые будут использоваться в дальнейшем. Это задача совместного планирования вычислений, передачи данных и размещения данных в памяти.

3.2. Ограничения расписания

Один ресурс — одна операция

На каждой линии операции не пересекаются:

[si, ei) ∩ [sk, ek) = ∅

Отдельно для Compute, H2D и D2H. Между разными линиями перекрытие разрешено.

Зависимости задач

Если задача j зависит от i, то:

sj ≥ ei

Compute не может нарушать порядок зависимых вычислений.

Готовность входов

Все необходимые чанки должны быть доступны в GPU к старту Compute:

sj ≥ eH2D(c)

Для каждого входного чанка c, который требуется загрузить.

Ёмкость GPU

В любой момент сумма резервирования резидентных чанков не выше ёмкости:

Σc ∈ GPU(t) qc ≤ M

qc — зарезервированный объём чанка, M — ёмкость GPU.

Дополнительное условие: все чанки задачи закреплены в GPU на всём интервале её Compute. Поэтому нельзя вытеснить вход задачи посередине вычисления, даже если отдельный чанк уже не читается в конкретной инструкции.

3.3. Размер данных и размер резервирования

В текущем режиме fixed-slot хэндл размера S разбивается на чанки ширины B:

N = ⌈S / B⌉

Для каждого чанка c определяется фактический размер sc и резервируемый размер qc. В fixed-slot каждый чанк занимает слот ширины B, включая последний неполный чанк:

qc = B  ;   0 < sc ≤ B

Время передачи считается по фактическому объёму, а память — по резервируемому:

tH2D,c = sc / vH2D  ;   tD2H,c = sc / vD2H

Таким образом, размер чанка влияет сразу на две вещи: внутреннюю фрагментацию GPU-памяти и количество/длительность операций передачи.

3.4. Жизненный цикл чанка и актуальность версии

Для планирования важно различать нахождение чанка в GPU и наличие актуальной копии на CPU. Упрощённо состояние чанка можно описать парой признаков: резидентен ли он в GPU и совпадает ли CPU-копия с последней версией.

СостояниеСмыслМожно ли освободить GPU?
ЧистыйGPU-данные совпадают с актуальной копией на CPUДа, без D2H
Грязный, живойGPU содержит новую версию, которая понадобится позже; CPU-копия устарелаТолько после сохранения актуальной версии D2H
Грязный, мёртвыйНовая версия больше не будет прочитана в оставшейся трассеМожно отбросить без D2H, если нет другого обязательства сохранить результат
Не резидентенЧанк отсутствует в GPUДля следующего чтения требуется загрузить актуальную версию

Запись меняет актуальность версии в конце Compute, а не в момент старта задачи. Это важно: пока Compute выполняется, входные чанки закреплены, а новая версия ещё не считается готовой.

Если грязный чанк понадобится в будущем, сначала должна завершиться D2H, сохраняющая эту версию на CPU. Только после завершения передачи слот можно освободить и повторно использовать. Для чистого чанка обратная передача не нужна.

3.5. Почему выбор вытеснения — часть глобального расписания

При нехватке памяти нужно выбрать набор чанков для освобождения. Ближайшее следующее использование — полезная оценка ценности резидентности. Классическая идея Belady предлагает вытеснять элемент, следующее использование которого дальше всего в будущем. Но в нашей задаче чанки имеют разные размеры, а вытеснение грязного чанка может потребовать D2H.

Поэтому решение нельзя принимать только по расстоянию до следующего использования. Учитываются:

  • когда чанк понадобится снова;
  • сколько памяти освободится после его удаления;
  • чистый он или грязный;
  • понадобится ли D2H и сколько она займёт;
  • когда новая версия станет готова к сохранению;
  • когда освободившаяся память понадобится следующей задаче;
  • можно ли перекрыть D2H с Compute, не блокируя запуск нужных задач.
Ключевой принцип: после последнего использования чанк становится кандидатом на вытеснение, но это не означает, что его нужно удалить немедленно. Планировщик выбирает допустимый момент освобождения в контексте будущей потребности в памяти и занятости каналов.

3.6. Иллюстративный пример

Рассмотрим условную GPU-память ёмкостью 2 слота по 1 МиБ. После первой задачи в GPU находятся чанки A и B. Чанк A чистый, а B содержит изменённую версию, которая понадобится следующей задаче. Для следующей задачи нужны B и C.

В этом примере вытеснение A не требует D2H: CPU уже содержит актуальную копию. B нельзя вытеснить до следующего Compute, поскольку он нужен этой задаче. Если бы вместо A требовалось освободить живой dirty-чанк D, пришлось бы сначала выполнить D2H(D), дождаться её завершения и только затем сделать DROP(D). Эта дополнительная передача могла бы задержать H2D(C) или занять канал D2H параллельно с Compute — в зависимости от доступности ресурсов и момента готовности версии.

3.7. Как текущая реализация ищет расписание

Текущий Global Planner — эвристический поиск среди нескольких полных вариантов расписания, а не решение общей задачи целочисленной оптимизации. Публичная точка входа сначала получает результат внутреннего планировщика, затем при необходимости строит дополнительные варианты и сравнивает их по фактическому makespan.

  1. Базовый кандидат. Внутренний планировщик строит начальный вариант через поиск резидентности и упаковку операций по временным линиям.
  2. Оценка нижней границы. Вычисляется нижняя оценка makespan. Если найденное расписание уже достигает её с допуском 1 мкс, дальнейший поиск в этой ветке прекращается.
  3. Преобразование ранних записей. Проверяется вариант, в котором D2H перемещается ближе к моменту, когда версия была создана последней записью и зарезервирована в GPU.
  4. Перебор конфигураций эвристики. Рассматриваются сочетания параметров порядка спроса, освобождения мёртвых данных, пропуска перезаписанных данных, предзагрузки, освобождения свободной памяти и приоритета крупных чанков.
  5. Локальные варианты около простоев. Внутренний оптимизатор может пробовать разделение резидентности отдельных хэндлов около наиболее длинных промежутков между Compute; число таких проб ограничено.
  6. Выбор лучшего. Каждый кандидат проходит упаковку/проверки временных линий. Сохраняется вариант с наименьшим makespan среди рассмотренных.

В публичной обёртке core/global_planner.py после результата внутреннего оптимизатора дополнительно проверяются четыре сочетания двух переключателей: prefetch_next и spill_idle. Для этих вариантов используется заданный режим demand-order, освобождение dead-чанков, пропуск перезаписанных данных и fastest-release. Сравниваются исходный кандидат и вариант с преобразованием ранних D2H.

Граница гарантии. Перебираются только предусмотренные кодом варианты эвристик и ограниченное число локальных преобразований. Это не полный перебор всех допустимых расписаний. Поэтому выбранный результат — лучший из проверенных кандидатов, но не обязательно глобальный оптимум.

3.8. Роль точного решателя

Для маленьких фиксированных задач используется независимый событийный поиск exact_small.py. Его состояние включает индекс следующей задачи, маски резидентных и dirty-чанков, остаток Compute и активные операции H2D/D2H с оставшимся временем. Поиск перебирает допустимые переходы между такими состояниями и находит минимальное время завершения в рамках заданной модели.

Текущие ограничения точного решателя: fixed-slot allocation, не более 10 чанков и 12 задач, а также ограничение бюджета состояний (по умолчанию 200 000). Если бюджет исчерпан, решатель сообщает об этом; он не выдаёт эвристическую оценку за точный оптимум.

Сравнение Global Planner с exact solver на малом графе позволяет измерить разрыв между эвристическим результатом и оптимумом именно для этого графа. Оно не доказывает оптимальность планировщика на больших трассах.

5. Корректность и проверка оптимальности

Проверяемые ограничения

  • GPU-память не превышает заданную ёмкость.
  • Каждый канал выполняет не более одной операции одновременно.
  • Compute начинается после подготовки необходимых данных и зависимостей.
  • Используются актуальные версии данных.
  • Необходимая D2H завершается до освобождения соответствующего чанка.
  • Все задачи графа завершаются.

Два уровня проверки

Автоматические тесты. Проверяют отдельные правила движка, обработку чанков, конкурентные инварианты, prefetch, интерфейсы и регрессионные сценарии. Для небольших графов результат Global Planner сравнивается с точным решателем.

Независимая проверка расписания. Скрипт-валидатор проверяет временные интервалы, каналы, вместимость памяти, доступность данных и часть условий версионности и безопасного вытеснения. Наличие валидатора не означает, что все возможные ошибки версионности и конкурирующего доступа уже формально исключены.

Что означает точный оптимум. Совпадение эвристического расписания с результатом exact solver доказывает оптимальность только для конкретной малой задачи и в рамках совпадающих допущений модели. Совпадение на конечном наборе тестов не доказывает глобальную оптимальность эвристики для произвольных трасс.

В точном поиске используются ограниченные по размеру постановки; при превышении бюджета состояний решатель сообщает об исчерпании бюджета, а не подменяет оптимум оценкой.

6. Эксперименты и метрики

Для оценки расписания используются следующие показатели:

МетрикаЧто показывает
MakespanВремя завершения последней обязательной операции — основная целевая метрика.
Compute / H2D / D2H busy timeСуммарное время занятости каждой линии с учётом объединения пересекающихся интервалов.

H2D / D2H bytesОбъём трафика между CPU и GPU.
Peak GPU memoryМаксимальный объём занятой или зарезервированной GPU-памяти.
Compute idle timeВремя, когда вычислительная линия не выполняет Compute.

Важно: 100% загрузка хотя бы одного канала не является обязательным критерием оптимальности. Простои могут быть неизбежны из-за зависимостей задач, доступности данных и ограничений памяти.

Воспроизводимое сравнение реальных трасс

Для сравнения базовых политик и Global Planner используйте benchmark-скрипт. Пример параметров ниже — конфигурация эксперимента, а не универсальные настройки алгоритма.

python scripts/benchmark_nntile_graph.py examples/tasks_mbs1.rec \
  --capacities-mib 768 1024 1536 \
  --h2d-gbps 12 \
  --d2h-gbps 12 \
  --chunk-mib 0.75 \
  --output results/global_comparison/benchmark.csv

Скрипт формирует CSV с метриками и отдельный CSV с событиями расписаний. Для второй трассы замените tasks_mbs1.rec на tasks_mbs4.rec.

В этом обзорном документе не приводятся численные результаты makespan для текущего Global Planner: их следует получать повторным запуском benchmark на выбранной конфигурации. Старые числа из предыдущих исследовательских срезов не переносятся сюда как актуальные.

7. Интерактивный NNTile Dashboard

Dashboard — локальная веб-панель для запуска симуляций и сравнения расписаний. HTML-интерфейс обращается к Python-серверу, который читает трассы, запускает алгоритмы и возвращает метрики и события. Открытие HTML-файла напрямую через GitHub Pages не запускает Python-бэкенд.

Запуск локально

  1. Откройте терминал в корне репозитория.
  2. Активируйте виртуальное окружение:
source .venv/bin/activate
  1. Запустите сервер:
python dashboard_server.py
  1. Откройте в браузере:

Терминал с сервером должен оставаться открытым. Для остановки нажмите Ctrl+C.

Возможности панели

  • Выбор доступной трассы из каталога examples/.
  • Независимый выбор алгоритмов LRU, Belady и Global Planner.
  • Настройка объёма GPU-памяти, пропускной способности H2D/D2H и порядка Compute.
  • Настройка размера чанка Global Planner; значение по умолчанию — 0,75 МиБ.
  • Сравнение makespan и других метрик, просмотр временной диаграммы и использования GPU-памяти, изучение событий расписания.

Панель предназначена для локальных воспроизводимых экспериментов. Для доступа коллегам через интернет потребуется отдельно развернуть Python-бэкенд; публикации одного HTML-файла недостаточно.

8. Текущее состояние и ограничения

РеализованоДвижок симуляции; LRU и Belady demand-only; глобальное эвристическое планирование; чанки; модель H2D/D2H и dirty data; benchmark; валидатор; Dashboard.
ПроверяетсяКорректность расписаний на тестовых сценариях; сравнение с точным решателем на малых задачах; качество эвристик на реальных трассах.
Не гарантируетсяГлобальная оптимальность для произвольной трассы; полнота формальной проверки всех возможных конфликтов версий и доступа.
  • Global Planner остаётся эвристическим: для произвольных графов оптимальность не гарантируется.
  • Точный решатель применим только к небольшим задачам и поддерживаемым допущениям.
  • Набор регрессионных сценариев не покрывает все сочетания размеров чанков, зависимостей, версий и конкуренции ресурсов.
  • Результаты зависят от конфигурации: объёма GPU-памяти, размеров чанков, скоростей передачи и порядка Compute.
  • Симуляция не заменяет измерения на реальном оборудовании.

Следующие направления работы

  • Продолжать находить малые контрпримеры, где эвристика не достигает точного оптимума.
  • Уточнять причины простоев Compute и разделять ограничения зависимостей, памяти и передачи данных.
  • Расширять независимую проверку версий данных и конкурирующих операций.
  • Сравнивать Global Planner с точным решателем там, где размер задачи позволяет это сделать.
  • Проводить воспроизводимые сравнения на реальных трассах и фиксировать параметры каждого эксперимента.
